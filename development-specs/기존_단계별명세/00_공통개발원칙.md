# 우당탕! 수학 레스토랑 2.0 — 공통 개발 원칙

> 모든 단계에 적용되는 마스터 명세. Claude Code는 단계별 작업을 시작할 때 이 파일을 먼저 읽는다.

## 게임 목표
초등 6학년 2학기 수학을 자연스럽게 복습하는 오리지널 2.5D 탑다운 요리 게임. 4~5인 협동 주방, 4인 2대2, 20~25명 학급(4~5명씩 독립 주방) 대항전을 지원한다. 학생마다 PC 1대. 학생은 별도 가입 없이 학급방 코드와 별명으로 입장한다. Overcooked의 분주한 협동 게임성은 참고하지만 원작 그래픽·맵·캐릭터·사운드를 복제하지 않는다.

**최우선 완성 시나리오:** 학생이 재료통에서 고기를 가져와 화덕에 올리고 수학 문제를 풀어 조리를 시작한다. 고기가 굽히는 동안 다른 작업을 한다. 완료 게이지와 타기 경고가 보이고, 제시간에 꺼내어 다른 친구가 준비한 빵과 함께 접시에 담는다. 접시에 빵·고기가 실제로 보인다. 완성 접시를 누군가 직접 들어 서빙한다. 주문 카드가 사라지고 점수가 오른다. 잘못 집은 손질 전 토마토는 원래 토마토통에 무료 반환한다. 손질 후 재료는 5칸 보관대 또는 -8점 쓰레기통으로 처리한다. 마지막 40초는 이동속도 135%, 새 주문이 약 10초마다 추가되어 최대 3개 동시에 처리한다.

## 반드시 유지할 기능
- 현재 동작 중인 메뉴, 6학년 2학기 6개 단원 문제, 교사 학급방, 팀 편성, Firebase 연결 코드, 결과 CSV, 단독 체험판.
- 프로젝트의 기존 파일(`index.html`, `game.js`, `style.css`, `cloud.js`, `firebase-config.js`, `database.rules.json`, `standalone-demo.html`)부터 검사하되 실제 구조가 다르면 저장소의 코드를 기준으로 파악한다.
- 기존 구현을 무조건 갈아엎지 말고 기능이 동작하는 최소 단위로 점진적 리팩터링. 기존 Firebase 설정값·비밀값을 로그·산출물에 노출하지 않는다.
- GitHub Pages 등 정적 호스팅과 호환되는 구조 우선. Firebase 없이도 체험판은 동일한 주요 규칙으로 실행되어야 한다.

## 도메인 규칙 (단계별 모두 일관되게)
1. **아이템**: 고유 ID, 종류, 손질 상태(`raw`, `prepared`, `cooking`, `cooked`, `burnt` 등), `sourceBinId`, 위치(`held`, `station`, `storage`, `plate`, `trash` 등), 소유 플레이어/작업대, 조리 시각을 갖는다. *하나의 아이템은 동시에 한 장소에만 존재한다.*
2. **원재료**: 손질 전에는 가져온 **바로 그 재료통**으로 E/Space 반환, 무료. 다른 통에 반환 불가. 원재료는 기본적으로 보관대·쓰레기통 투입 불가. Q 즉시 삭제 삭제.
3. **손질 후**: 원재료통 반환 불가. 보관대에 최대 5개(원하는 아이템 선택 회수) 또는 쓰레기통 폐기 -8점. 탄 재료는 보관/서빙 불가, 폐기만 허용. 점수는 0 미만 불가.
4. **도마**: 수학 문제 정답으로 작업 권한 확보 → Space 또는 E **실제 연타**로 게이지 상승 → 작업 모션/도마 흔들림/재료 파편/효과음 → 완성. `event.repeat`는 연타 횟수로 세지 않는다. 초등학생의 부담을 줄이도록 난이도 상수를 둔다.
5. **화덕**: 팬/오븐에 올려두면 시간이 자동 흐른다. 플레이어는 떠나 다른 일 가능. 진행 게이지→완료→과조리 경고→탄 상태. 다시 돌아와 직접 집는다. 점유 설비에는 다른 재료를 동시에 올릴 수 없다.
6. **그 밖의 설비**: 믹서, 싱크대(설거지), 접시대에도 모션과 진행 게이지. 설비별 점유 상태·재료명·진행 상황이 화면에 표시되어야 한다. 경쟁 상황에서 두 플레이어가 같은 작업을 중복 완료할 수 없다.
7. **접시**: 접시/트레이에 놓인 재료가 월드 화면에 **재료별로 식별 가능**. 주문별 조합·완성 여부 추적. 접시를 직접 들어 서빙대로 옮겨야 점수 획득(단순 tray 플래그→즉시 서빙 금지). 서빙한 접시는 더러워지고 설거지 후 재사용한다. 초기 깨끗한 접시 수는 밸런스 조정 가능.
8. **주문**: 좌측 상단에 실제 레시피 카드(완성 이미지, 재료, 각 조리 아이콘, 남은 대기 게이지) 노출. 고유 `orderId`, `recipeId`, 생성/만료 시간, 완료 상태. 기본 1개, 러시타임 최대 3개 동시 활성. 개별 주문과 개별 접시를 일관되게 연결한다.
9. **러시타임**: 남은 40초, 짧은 라운드는 마지막 20% 시점부터 발동. 이동속도 135%, 모션 속도도 상향, 러시 시작 시 추가 주문, 이후 약 10초마다 새 주문(최대 3개). 주문이 **진짜로 플레이 가능**해야 한다. 붉은 펄스/경고음/속도감. 타이머·콤보 서버 기준 일관성.
10. **점수·경쟁**: 주문 기본 100점, 14초 내 연속 서빙 시 +20씩 콤보(상한 설정 가능); 손질 후 폐기 -8점. 주문 지연 시 **팁 보너스만** 약하게 감소. 4인 2대2는 2명씩, 5명팀은 팀간 대항전(불합리한 2대2 배분 금지), 다른 팀 인원과 점수 비교 시 공정한 보정 사용. 수학 빠르기만으로 승패 결정되지 않게 한다.
11. **수학**: 1 분수의 나눗셈, 2 소수의 나눗셈, 3 공간과 입체, 4 비례식과 비례배분, 5 원의 둘레와 넓이, 6 원기둥·원뿔·구. 수학 문제는 작업 시작/단계 해금에 자연스럽게 연결하고, 매 연타마다 문제를 요구하지 않는다. 오답 힌트·재도전, 학생별 풀이 기록. 개념/정답 검증.
12. **교육적 접근성**: 빠른 연타와 시간 압박은 교사 설정으로 완화할 수 있도록 난이도·접근성 옵션 계획. 계산 중인 학생에게 불가피한 일방적 페널티를 주지 않는다.

## 설계/보안/테스트 규칙
- 로컬 데모와 Firebase 모드가 **같은 게임 규칙/상태 전이 로직**을 쓰도록 도메인 모듈 분리(예: `itemModel`, `stationLogic`, `orderLogic`, `scoring` — 파일명은 프로젝트 상황에 맞춰 결정).
- 공유 주방의 아이템 이동, 조리대 점유, 서빙, 보관대 입출고, 점수는 경쟁 상태를 고려해 원자적으로 처리한다. `Date.now()`만으로 다중 클라이언트 권한을 신뢰하지 않는다.
- 교사 권한을 학생이 임의 주장할 수 없도록 확인해야 한다. **익명 학생 로그인 허용 ≠ 교사 관리자 권한 누구나 허용**. Firebase Rules/Cloud Functions 등으로 검증 가능할 때만 '보안 구현 완료'라고 보고한다.
- 다른 학급/학교의 `rooms/{roomId}` 와 다른 팀 데이터에 대한 읽기·쓰기 접근은 권한/경로로 제한한다.
- 테스트 가능한 게임 상태는 단위 테스트, 사용자 흐름은 브라우저에서 실제 조작으로 확인한다. 테스트 환경에 Firebase 인증·멀티 브라우저가 없다면 '미검증'을 명시하고 가짜 성공을 보고하지 않는다.
- 각 단계가 끝나면 **(1) 바뀐 파일 (2) 구현 기능 (3) 테스트 방법/결과 (4) 남은 문제 (5) 다음 단계 영향**을 요약한다. `DEVLOG.md`와 `TEST_CHECKLIST.md` 갱신. 자동으로 다음 단계로 넘어가지 않는다.
- 단계마다 기존 플레이 루프(재료 집기→가공→접시→서빙)가 가능한 **실행 가능한 코드**를 남긴다. 브레이킹 변경이 필요한 경우 구버전 호환/일시 어댑터를 둔다.
- 아래 단계 중 해당 단계만 구현한다. 아직 요청되지 않은 다음 단계의 대규모 기능 개발은 하지 않는다. 화면과 플레이 테스트 없이 '완성'이라고 주장하지 않는다.
